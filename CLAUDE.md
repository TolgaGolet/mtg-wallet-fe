# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

React 18 frontend (Vite, plain JavaScript with JSDoc types, no TypeScript files) for [MTG Wallet BE](https://github.com/TolgaGolet/mtg-wallet-be), a Spring Boot personal-finance API (transactions, accounts, payees, categories, JWT auth with email verification and TOTP 2FA). UI is built with Mantine v7, react-router 7 and `@tabler/icons-react`. Deployed at https://mtgwallet.onrender.com (Render static site, publishes `build/`). Node 22.12+.

## Commands

- `npm start` (or `npm run dev`): Vite dev server on port 3000 (`strictPort`; the backend's CORS allowlist expects it).
- `npm run build`: production build into `build/`. `npm run preview` serves it.
- `npm test`: Vitest in watch mode; single run `npm test -- --run`; one file `npm test -- path/to/file`; by name `npm test -- -t "name"`. Tests sit next to the code (`*.test.js(x)`); config is the `test` block in [vite.config.js](vite.config.js) (jsdom, globals, `VITE_*` test values). [src/setupTests.js](src/setupTests.js) registers jest-dom on both Vitest `expect` instances (with `globals: true` they differ) and polyfills `matchMedia`/`ResizeObserver` for Mantine.
- `npm run lint`: ESLint 9 flat config ([eslint.config.js](eslint.config.js)), `--max-warnings=0`. The build no longer lints (CRA did), so run it. There are no `eslint-disable` comments; keep it that way (use `useApiQuery` / `useStableCallback` instead of suppressing `exhaustive-deps`). `prefer-const` is on. ESLint stays on 9 until `eslint-plugin-react` supports 10.
- `npm run typecheck`: `tsc -p jsconfig.json`. Only files starting with `// @ts-check` are checked (shared components, hooks, `api/`, `utils/`); give new shared components JSDoc prop types and `// @ts-check`. App-specific axios options (`silentErrors`) are declared in [src/api/axios.d.ts](src/api/axios.d.ts).
- `npm run format` / `npm run format:check`: Prettier (`.prettierrc`: es5 trailing commas) over `src/`.
- Files containing JSX must be `.jsx` (Vite only transforms JSX there).

## Configuration

All API endpoints come from `VITE_*` env vars, read as `import.meta.env.VITE_*` (base URL, login/refresh/logout/sign-up/verify-email paths, and the localStorage key for auth tokens). For local dev, copy `.env.example` to `.env`, which is gitignored. Production values live in Render's environment settings. Vite bakes them in at build time (they end up in the bundle, so never put secrets there); restart the dev server after changing them. `vite.config.js` lists every required one (`REQUIRED_ENV`) and stops dev/build when one is missing; add new vars there.

## Architecture

- **Entry/providers** ([src/index.jsx](src/index.jsx)): `StrictMode` → `MantineProvider` (auto color scheme) → `Notifications` → `ModalsProvider` → `DatesProvider` (user's timezone, Monday first). `index.html` is at the repo root. `userTimezone` lives in [src/utils/timezone.js](src/utils/timezone.js) (not in `index.jsx`, so nothing imports the entry point). StrictMode runs effects twice in dev: effects must clean up, and anything that must not repeat (single-use token POSTs) is deduplicated (see `TokenActionPage`).
- **Routing** ([src/App.jsx](src/App.jsx)): a single `createBrowserRouter` tree. The root route wraps `AuthProvider` + `ScrollToTop` (top on a pathname change only, so paging and filters keep the position) + `RootLayout` (AppShell with nav). Authenticated pages are children of one pathless `<Route element={<PrivateRoute />}>`, which redirects to `/login` when `user` is absent. Route paths are kebab-case (`/helpContact` only redirects to `/help-contact`). Every page except Home, Login and NotFound is `React.lazy`-loaded (its own chunk); `RootLayout` wraps the `<Outlet />` in `Suspense`, and the root route's `errorElement` ([RouteError](src/pages/RouteError.jsx)) catches render errors and chunks that fail to load after a deploy. The menu items come from one `NAV_ITEMS` list in [RootLayout](src/layouts/RootLayout.jsx), rendered as `NavLink`s (real links with `aria-current`); the mobile `AppShell.Navbar` (itself a `<nav aria-label="Main">`) is mounted only while open and closes when the window widens past `sm` (one "Main" landmark, no off-screen tab stops).
- **Auth** ([src/context/AuthContext.jsx](src/context/AuthContext.jsx)): stores `{accessToken, refreshToken}` in localStorage; `user` is derived from the access token (never stored separately). Its functions return results instead of touching page state: `loginUser(credentials)` resolves to `{ status: "ok" | "totp" | "error", message, isEmailVerificationRequired }`, `signUpUser(data)` rejects on error, `logoutUser(message?)` (sends the access token, or the refresh token once the access token has expired, so the backend can revoke the session). Pages own their loading/error UI; success dialogs use `openSuccessDialog`. A `storage` listener follows logins/logouts/refreshes from other tabs; it only updates the user (`PrivateRoute` redirects protected pages, public pages such as reset password stay put). Default categories and payees are created by the backend when the email is verified, not by the frontend. An endpoint that rotates the session (e.g. `auth/totp/verify-setup` revokes every token and answers a new pair) must pass the answer to `adoptTokens(tokens)`, or the next request logs the user out. Tokens in localStorage are readable by any XSS: a known trade-off, to revisit in the security audit (httpOnly cookies need backend work).
- **API calls** ([src/api/client.js](src/api/client.js)): one module-level axios instance (60 s timeout, sized for Render cold starts). Pages get it through `const callApi = useAxios();` ([src/utils/useAxios.js](src/utils/useAxios.js)) and call `callApi.get/post/put/delete("resource/action", ...)` with paths relative to the base URL. `AuthProvider` hooks it up to React state through `configureAuth`. The client:
  - refreshes expired access tokens before requests and retries once on 401/403. All callers share one in-flight refresh, which is cleared when it settles. Refreshes are serialized across tabs with `navigator.locks` (refresh tokens are single-use), and a tab that waited, whose refresh lost to another tab, or whose request got a 401 because another tab rotated the tokens (`refreshTokens(sentAccessToken)`), uses the tokens the other tab stored. It logs out (once, while tokens are still stored) when the refresh token has expired or the refresh gets 401/403; network errors, 429 and 5xx (Render cold start) keep the session;
  - **shows the error toast itself**: the string body of an error response, a 429 message, or a network-error message (never for aborted requests). Callers don't add their own error toasts;
  - `publicApi` (same file) is the interceptor-free client for the public auth endpoints (login, sign-up, password reset, email verification, account recovery); there is no raw `fetch` in `src/`. Pass `{ silentErrors: true }` when a page shows the error itself, and use `getErrorMessage(error)` to read the server's text; background requests that outlive a page pass `{ sessionUser: user.sub }` (cancelled if the session is someone else's) and clear their module state via `onSessionChange` (fired by AuthContext on logout / user switch), as `pages/Home/homeCurrencySave.js` does;
  - expected backend errors carry an `X-Error-Code` header (the backend's error constant name); read it with `getErrorCode` ([src/api/errorCodes.js](src/api/errorCodes.js)) instead of matching message text;
  - **sends top-level `Date` fields as local wall-clock strings** (`YYYY-MM-DDTHH:mm:ss`, via `toLocalDateTime` in [src/utils/dates.js](src/utils/dates.js)), because the backend stores `LocalDateTime` in the user's local time. Nested Date fields are not converted.
- **Loading data** ([src/utils/useApiQuery.js](src/utils/useApiQuery.js)): `useApiQuery((signal) => callApi.get(..., { signal }).then(r => r.data), [deps], { onSuccess, enabled })` returns `{ data, loading, error, retry }`. Always pass `signal`: the hook aborts stale requests when deps change or on unmount, so out-of-order responses can't win. Render `ListSkeleton` while loading and `<LoadError onRetry={retry} />` on error. Forms fill their values in `onSuccess`, not in an effect. Pass `enabled: false` while an input isn't known yet (the query stays idle) instead of returning null from the fetcher. Paged lists (`POST <entity>/search`) use `usePagedSearch(path, body)` ([src/utils/usePagedSearch.js](src/utils/usePagedSearch.js)) and `PagedFooter`: the page lives in `?page=` (1-based, `replace` navigation), so it survives returning from an edit form, an emptied last page moves to the new last one, and a changed `body` (filters) starts at page 1 by itself in one request, so callers never reset the page; `reload()` searches again from page 1. Transactions keeps its filter form values in `?filter=` too (`transactionFilter.js`), changed together with the page in one navigation, so a refresh or Back keeps the filter with its page. Pagination shows only for more than one page. For effects that should run only on certain values but read current state, wrap the handler in `useStableCallback` ([src/utils/useStableCallback.js](src/utils/useStableCallback.js)).
- **Validation** ([src/validation/rules.js](src/validation/rules.js)): every form rule (regexes, lengths, `LIMITS`, Mantine validators) lives here and mirrors the backend's request validation; `rules.test.js` pins the regexes to the backend strings, so a change must be made on both sides. Login and "confirm your password" fields only check that the password isn't empty (`requirePassword`). Forms validate on blur; password forms (sign-up, reset, change password) and TOTP code fields validate on change on purpose, for live strength/match feedback. Every 6-digit code field spreads `TOTP_INPUT_PROPS` (number pad, code autofill). `AMOUNT_MAX` caps typing in amount inputs below the backend's 16 digits, because JS numbers hold ~15 exactly; `AmountInput` never clamps (that would silently change a larger stored value), so forms add `validateAmountMax`.
- **Backend conventions**: listing is done with `POST <entity>/search` (body = filters, `params: { pageNo }`), and responses are Spring pages (`content`, `totalPages`, `totalElements`; use `totalElements` for limit checks). Single records load with `fetchById(callApi, entity, id, signal)` ([src/api/fetchById.js](src/api/fetchById.js)): the backend answers an empty page (not 404) for a missing, deleted or foreign id, so it throws a not-found error (`isNotFound(error)`) and pages render `NotFoundState` instead of an empty form. Updates go to `PUT <entity>/update/:id` and deletes to `DELETE <entity>/delete/:id`. `transaction/search` OR-s `sourceAccountId` and `targetAccountId`, so an account filter sends the same id as both.
- **Page patterns** ([src/pages/](src/pages/)): pages are grouped per entity folder. Form fields holding ids are named `...Id` (Select values are strings: `idString` / `toId` in [src/utils/ids.js](src/utils/ids.js)), and requests are built explicitly with the fields the backend request class accepts (never spread a server object into a request). Create and edit share one component on route `<entity>/create-or-edit/:id`, where the literal id `create` means create mode. Account, Category and Payee forms use `useEntityForm` + `EntityFormPage` ([src/components/entityForm/](src/components/entityForm/)): the hook loads `<entity>/create/enums` and the record, submits with the page's `toCreateRequest` / `toUpdateRequest`, and confirms deletes; after an update it goes back to the page that opened the form (`afterUpdatePath` only when opened directly), so history has no duplicate. The page keeps only its fields and mappers. Accounts, Categories and Payees lists are thin wrappers around `PagedEntityList` (Accounts passes its own card via `renderItem`). Pages opened from email links (verify email, recover account) use `TokenActionPage`, which posts each token once (a failed request is forgotten and network/5xx failures offer Retry). The password checklist is `components/PasswordStrength`. Confirmations and dialogs use `modals` from `@mantine/modals`. After a save, refetch what the page shows (`retry`) instead of `window.location.reload()`.
- **Shared components** ([src/components/](src/components/)): `showNotification(message, "success" | "error")` is the only way toasts are shown (an identical message within 1 s is dropped, so a burst of failing requests shows one toast but a user's repeated action still shows each result; non-error toasts are capped at 5 per 5 s, errors never). `ClickableCard` is the clickable card for rows and list items (a link with `to`, otherwise a keyboard-operable button; always pass `aria-label`). `TransactionRow` takes the `transaction` object from `transaction/search`. `PageTitle`'s back button goes back in history, or to `backTo` (default `/`) when the page was opened directly. `ListSkeleton` and `LoadError` cover loading and error states, `NotFoundState` a missing record, `openDeleteConfirm` every delete confirmation (Mantine's `Alert` always has `role="alert"`, so don't use it for empty states). `AmountInput` / `AmountFormatter` enforce 2-decimal, `.` decimal / `,` thousands formatting, and `AmountInput` is bound via `form` + `fieldName`. Enums such as `Currency`, `Interval` and `TYPE` (transaction types `EXP`/`INC`/`TRA`, plus `TYPE_LABEL` / `TYPE_OPTIONS`, the only place type labels are defined) live in [src/enum/](src/enum/); use `TYPE` instead of the string literals.
- **Accessibility**: clickable things must be real buttons or links (or `ClickableCard`), icon-only controls need an `aria-label`, form controls need a `label`, status changes are announced (`role="status"`), and meaning can't rely on colour alone (amounts carry a +/− sign).
- **Styling**: Mantine props first; component-specific CSS goes in co-located `*.module.css` files. Hover and focus styles belong in CSS (`:hover`, `:focus-visible`), not in mouse handlers. PostCSS ([postcss.config.cjs](postcss.config.cjs)) provides `postcss-preset-mantine` and `$mantine-breakpoint-*` variables.
- **TransactionModal** ([src/components/TransactionModal/](src/components/TransactionModal/)): the create/edit transaction dialog used by Home, Transactions and Account Detail, always through `LazyTransactionModal`, which mounts it only while open (every opening starts fresh, so there is no reset logic) and loads its chunk, including `@mantine/dates`' DateTimePicker, on first use. Data loads in `useTransactionFormData` (enums, recent transactions, and the transaction by id in edit mode); `loadedRecentTransactions` only feeds the quick-pick suggestions (`suggestions.js`). `onSaved` tells the parent to refetch. Transfer rules (distinct target, same currency) are pure functions in `accountRules.js`, payee search lives in `usePayeeSearch`, and the request shape in `buildTransactionRequest` (`transactionRequest.js`).
- **Text and number helpers**: `includesIgnoringCase` / `sameName` ([src/utils/text.js](src/utils/text.js)) for case-insensitive matching (search folds with Turkish and browser-locale rules; `sameName` stays Turkish to match the backend), `formatAmount` / `accountOptionLabel` / `categoryLabel` ("Gas (Auto)") ([src/utils/format.js](src/utils/format.js)) for plain-text labels. Dates are displayed in the browser's locale.
- **Tests**: component tests render through `renderWithProviders` ([src/test/renderWithProviders.jsx](src/test/renderWithProviders.jsx); Mantine/Modals/Dates providers, a memory router, an optional AuthContext value, `user` and `location()`; `pickOption` picks a Select option, `fakeJwt` in `src/test/jwt.js` builds tokens) and mock `useAxios` with `vi.hoisted` + `vi.mock("…/utils/useAxios", () => ({ default: () => mockApi }))`. Name regression tests after the bug they pin.

## Related repos

- **Backend**: `../mtg-wallet-be` (Spring Boot 4 / Java 21, served under `/api` on `http://localhost:8080` locally). It has its own `CLAUDE.md` describing the controllers, DTOs, enums and error handling this app consumes.
- Changing what the UI sends or expects (fields, endpoint paths, enum `value`s, validation rules) usually needs a matching backend change. If the dev server origin changes, the backend's CORS allowlist (`SecurityParams.CORS_ALLOWED_ORIGINS`) must be updated too.
